# HTML まとめ

素材（会議の文字起こし・ボード・コード・調査メモ）を、読み手が一度読めば流れと決定事項をつかめる 1 枚の HTML にする。外部 JS を持たない単一ファイルなので、そのまま渡せて、どこで開いても同じ見た目になる。

## 使う / 使わない

**使う**: 会議やイベントストーミングのまとめ、設計の論点整理、意思決定の記録、データや処理の経路、before/after、PR の変更点の全体像。文章だけだと読み手が頭の中で図を組み立て直す必要がある題材。

**使わない**: 短い事実の回答（テキストで答える）、プロダクトの UI 実装、スライド、単なる列挙や手順（Markdown で足りる）。図が要らない題材に図を足さない。列挙は表、順序は番号つきリスト、対比は 2 列の箱で足りる。

## 手順

1. **素材を全部読む。** ボードは付箋と矢印の両方、文字起こしは最後まで読む。出典にないことは書かない。説明のために足した例は「例」と書く。
2. **読み手と結論を決める。** 誰が読み、読み終えて何ができればよいか。決まったことは冒頭に「決まったこと」としてカードで並べる。
3. **構成を議論や処理の順に並べる。** 「決まったこと → 前提 → 本体 → 持ち越した論点」が基本。話題が大きく 2 つ以上あるなら、`.part`（第1部・第2部）で区切って議論した順に置く。決まったことも部ごとに分ける。
4. **既存の見た目を探す。** 同じシリーズのページがあればそのトークンを引き継ぐ。プロジェクトにデザインシステムがあればそれが優先。なければ `assets/template.html` を使う。
5. **デザインの計画を `:root` に書く。** 色 4〜6 個、書体 3 役、レイアウトを 1 行のコメントで。返答に hex やフォント名を並べない。
6. **`assets/template.html` をコピーして中身を書く。** 使わない部品は消す。`【…】` のプレースホルダを残さない。
7. **図を描く。** 流れ・分岐・関係を見せる節にだけ、1 ページに 1〜4 枚。描き方は下の「図」と `references/design.md`。
8. **一度だけ確認して直す。** 下の「確認」。確認と修正を何度も繰り返さない。
9. **出力して場所を伝える。** 下の「出力と共有」。

## デザインの決め方

詳しい理由と CSS の書き方は `references/design.md`。ここでは判断だけを書く。

- **題材の世界から決める。** その題材にしかない細部を 1 つは入れる。例: イベントストーミングなら付箋の慣習色を状態の札（合意=緑・案=青・未決=マゼンタ・次回=灰）に使う。会計なら期間を `2026.10` と書き、数字の列に `font-variant-numeric: tabular-nums` を付ける。
- **書体は 3 役。** 見出しは特徴のある和文（Zen Kaku Gothic New）、本文は読みやすいもの（BIZ UDPGothic）、eyebrow やラベルは等幅（IBM Plex Mono）。Google Fonts から読み、必ずローカルのフォールバックを並べる。
- **色。** 背景は少し色味を帯びた中間色にする（純粋な灰色は避ける）。アクセント 1 色、登場人物や領域の色（`--z1`〜`--z4`）、状態の色を分ける。状態の色はアクセントとは別物として扱う。
- **ライトとダークの両方を作る。** トークンを `:root`、`@media (prefers-color-scheme: dark)` 内の `:root:not([data-theme="light"])`、`:root[data-theme="dark"]` の 3 か所に書く。部品は必ずトークン経由で塗る。`body` に背景色を明示する。
- **構造は情報を表すときだけ使う。** 番号は本当に順序があるときだけ。eyebrow・札・区切りは内容の事実（日付・状態・部）を表す。
- **枠は役割で付ける。** 決定のカード、付箋、図の枠、表にだけ枠を付ける。すべてのブロックに角丸と影を付けない。
- **生成 AI っぽい見た目を避ける。** クリーム地に明朝とテラコッタ、黒地に蛍光 1 色、紫から青のグラデーションのヒーロー、Inter や Space Grotesk、絵文字の見出し、全部中央寄せ、全部に大きな角丸、カード左端の色帯。ユーザーが指定したときはそれに従う。
- **開いた時点で完成している。** 大きなヒーローや 100vh の表紙を置かない。アニメーションに頼らない。

## 図（インライン SVG）

- **塗りはクラスとトークンで。** `.bx`（箱）・`.zn`（帯・領域）・`.ar`（矢印）・`.al`（矢印ラベル）・`.bt` / `.bs`（太字 / 補足）を使う。SVG に hex を直接書かない。
- **レーン図。** 登場人物（ユーザー / エージェントなど）ごとに横帯を引き、箱を同じ幅・同じ間隔の列に置く（例: 幅 140、ピッチ 166）。矢印は列の隙間の中央で直角に曲げる。こうすると線が箱を横切らない。
- **分岐。** 箱の右辺の別々の高さから出す。採用した案は実線と色付きの箱、見送った案は破線とグレーの箱にする。
- **戻り（修正指示など）。** 下の空いた帯を通して戻し、ラベルは線の上に背景色の縁取り（`paint-order: stroke`）で置く。
- **長い流れは 2 段に分ける。** 前半と後半で別の SVG にして、前半の終わりに「後半へ」のピルを置く。
- **marker の id はページ内で重複させない。** 図ごとに `c1` / `c2` のように変える。
- **`role="img"` と `aria-label` に図の主張を書く。** `figcaption` には図番号・主張・凡例（色や破線の意味）を書く。
- **`.fig-scroll` に入れて `svg` に `min-width` を付ける。** 狭い画面では縮めずに横スクロールさせる。

## 文章

- **結論から書く。** 冒頭に決まったこと。各項目に状態の札（合意 / 案 / 未決 / 次回 など）を付けて、決まったことと持ち越したことを見分けられるようにする。
- **出典にないことを足さない。** 推測と確認済みを分ける。未確認は未確認と書く。
- **資料の作り方に触れない。** 「ボードを描き直しました」「このページは〜をもとに整理したものです」「会議サマリーより」「ボード上段にあたります」は書かない。出典へのリンクは置いてよい。
- **見出しで読み手を決めつけない。** 「誤解の解消」のような見出しより、中立な問いや事実にする。
- **平易に、短く、能動態で。** ダッシュで挟む挿入句、「X ではなく Y」の言い回し、コロンのあとで種明かしする書き方、造語をかぎ括弧でくくる書き方、「注目すべきは」のような決まり文句を避ける。
- **人名を出さない。** 役割（参加者・運営など）で書く。
- **コードの題材では根拠を `path/to/file.go:42` で示す。** 数えたなら数を書く。
- **`<title>` は 2〜4 語の名前にする。** 説明はつけない（例:「決算管理イベントストーミング」）。

## 確認（1 回だけ）

```bash
python3 <このスキルのディレクトリ>/scripts/check_html.py page.html   # 構文・アンカー・id 重複・プレースホルダの残り
CH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
"$CH" --headless=new --disable-gpu --hide-scrollbars --window-size=1360,2400 \
  --screenshot="$PWD/preview.png" "file://$PWD/page.html"
```

スクリーンショットを画像として見て、箱と線・ラベルの重なり、箱からはみ出した文字、意図しない横スクロールだけを直す。直したあとにもう一度撮って見比べることはしない。プレビュー用のファイルは消す。見ていない観点（ダークテーマ・スマホ幅など）は報告に書く。

## 出力と共有

- **既定**: `<!doctype html>` から始まる完全な HTML を、作業用の scratchpad か指定された場所に書き、パスを伝える。
- **Claude Code の Artifact に出す場合**: `<!doctype>`・`<html>`・`<head>`・`<body>` を外し、`<title>`・`<link>`・`<style>` を先頭に置いた中身だけにする（公開時に骨格が付く）。
- **miru Page などに出す場合**: 完全な HTML を渡す。更新は、手元のファイルを直してから指示されたときだけ反映する。大きく組み替えたときは全文を置き換え、数か所の修正なら部分置換を使う。
- 公開済みのページと手元のファイルがずれたら、どちらが最新かを報告に書く。
