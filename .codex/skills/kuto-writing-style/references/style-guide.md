# kuto文体ガイド

このガイドは、公開済みのZenn記事を主資料、はてなブログの技術記事・コンペ振り返りを構成上の補助資料、Qiita記事を初期文体の参考資料として抽出したもの。過去記事の内容や結論を流用せず、説明の組み立て方と声の調子を再現する。

## 文体の核

kutoの文章は、専門的な内容を「自分が理解した順序」に沿って読者へ渡す、落ち着いた説明調である。権威的に断言するより、根拠を示したうえで理解・観察・解釈を分ける。親しみやすさはあるが、雑談や比喩を増やしすぎない。

- 一人称は「私」。読者への呼びかけは必要な場面だけにする。
- 本文は自然な「です・ます」調。見出しと箇条書きは簡潔な体言止めも使う。
- 技術的事実は明確に述べ、解釈は「〜と考えています」「〜という印象です」「〜を示唆しています」のように確度を調整する。
- 成功だけでなく、改善しなかった方法や疑問点も、試した目的と結果を添えて残す。
- 最後に少量の感情を出すことはあるが、本文全体を煽り口調にはしない。

## 情報の並べ方

基本原則は「背景・目的 → 全体像 → 詳細 → 結果と解釈 → まとめ」。最初から細部へ入らず、読者が現在地を把握できる案内を置く。

### 導入

導入では次のうち必要なものを短く示す。

- なぜ今この話を書くのか
- 何を読んだ、試した、または振り返るのか
- 記事で扱う範囲と扱わない範囲
- 想定読者または必要な前提知識
- 読者が記事から得られるもの

自然な型：

> 本記事では、Xを題材にYを試し、その結果と得られた学びを整理します。特にZに興味がある方の参考になれば幸いです。

「本記事では」を毎回機械的に使う必要はない。イベント、問題意識、実験のきっかけから入る方が自然ならそちらを選ぶ。

### 概要から詳細へ

- 長い記事では、前提、要約、問題設定、基本解法などを先に置く。
- 初出の専門用語は、日本語名、英語名、略称、記事内での意味を必要な範囲で説明する。
- 比較対象がある場合は、先に比較軸を示してから各項目を説明する。
- 詳細セクションは「何をするものか」を一文で案内し、その後に仕組みや結果を書く。
- 図表の後は「これを見ると」「上の結果では」などで、読み取れる内容を文章化する。

### 根拠から解釈へ

段落は可能な限り次の順にする。

1. 対象となる事実、手法、実験条件を示す。
2. 数値、図、比較、引用などの根拠を示す。
3. そこから分かることを説明する。
4. 必要なら個人的な解釈や実務上の意味を付ける。

観察と解釈を一文に押し込まず、確度が変わる地点で文を分ける。

## 記事タイプ別の骨格

以下は固定テンプレートではない。題材に必要な部分だけを選ぶ。

### 研究・論文紹介

- 背景と問題意識
- 記事の前提、または3行程度の要約
- 用語や歴史的背景
- 中心となる定義・議論・比較
- 代表研究を論点ごとに紹介
- 現時点での整理
- 個人的な解釈、実務への示唆
- おわりに、参考文献

対立する主張がある場合は、一方だけを正解として処理せず、双方の根拠を示してから暫定的な結論を置く。

### 実験レポート

- 試す動機
- 題材、モデル、条件、比較するアプローチ
- ベースラインから順に結果を提示
- 各結果について、良い点、気になる点、次に試す変更を説明
- 最終結果と実用性の評価
- 短い感想または今後の展望

条件は箇条書きで揃え、結果は画像や数値を貼るだけで終わらせず言語化する。

### コンペ・プロジェクトの振り返り

- 期間、課題、順位や成果、チーム構成
- タスク、データ、評価指標
- 基本方針または解法概要
- 時系列または構成要素ごとの取り組み
- 効果があったこと、効果がなかったこと
- 上位解法や他者の知見との比較
- 学び、反省、次に試したいこと

失敗例は省かず、「なぜ試したか」「何が改善しなかったか」「今ならどう見るか」を簡潔に添える。

### トラブルシューティング・手順

- 症状または結論を早めに提示
- 発生条件や環境
- 原因
- 対策の手順
- 制約、未確認点、別ケースへの注意

短い題材を不必要に長文化しない。

## 語彙と接続

よく馴染む接続表現：

- 順序：まず、次に、ここから、最後に
- 対比：一方、ただし、これに対して、〜ものの
- 因果：そのため、そこで、これにより、結果として
- 要約：このように、つまり、端的にいうと
- 具体化：例えば、具体的には、もう少し噛み砕くと
- 根拠の読み取り：これを見ると、〜ことがわかります、〜傾向が見られます
- 範囲の限定：本記事では、ここでは、前提として、なお

同じ接続語を連続させない。「このように」で各節を締めるなど、口癖の機械的な反復を避ける。

## 断定の強さ

根拠に合わせて表現を選ぶ。

- 強い根拠：〜を示しました、〜ことがわかります、〜を達成しています
- 傾向・限定的な結果：〜傾向が見られました、〜と考えられます、〜を示唆しています
- 個人的解釈：個人的には〜と感じました、〜という印象を持っています、〜と解釈しています
- 未検証・疑問：〜かもしれません、〜という疑念もあります、十分には確認できていません

「〜と思います」だけを重ねず、観察、推論、好みのどれなのかが分かる表現にする。

## 見出し・箇条書き・強調

- 見出しは内容を直接表し、過度に煽らない。
- 大見出しで論理の段階を示し、小見出しで比較対象や構成要素を分ける。
- 箇条書きは条件、分類、手順、比較軸に使う。長い議論は本文に戻す。
- 番号は順序や対応関係が重要なときに使う。
- 太字は中心命題、重要な観察、結論に限定する。
- コード、数式、図、表は、直前または直後の文章で役割を説明する。
- URLや引用は主張の近くに置く。参考文献一覧は長い調査記事で使用する。

## 表記

- 初出では「強化学習（Reinforcement Learning, RL）」のように日本語と英語・略称を対応させる。以後は略称でよい。
- 数値やモデル名、指標名は曖昧に言い換えず、そのまま示す。
- 日本語の句読点は「、。」を基本とする。
- 英数字と日本語の間隔、製品名の大文字小文字、見出し番号は記事内で統一する。
- 過去記事にある誤字、表記揺れ、壊れたリンク形式までは模倣しない。

## オリジナル例

### 結果の説明

> ベースラインでは処理時間を短縮できた一方で、精度はほとんど改善しませんでした。これを見ると、今回のボトルネックは推論部分ではなく前処理にある可能性が高そうです。ただし、検証したデータは1種類に限られているため、他の条件でも同じ傾向になるかは追加で確認する必要があります。

### 複数の主張を整理する

> ここまでの結果だけを見るとAが有効に見えますが、Bを支持する事例も存在します。そのため、AとBのどちらか一方が常に正しいというより、タスクの難易度と利用できるデータによって役割が変わると考えるのが自然そうです。

### 個人的な解釈へ移る

> ここからは、上記の結果をもとに私が考えたことを整理します。現時点での個人的な解釈であり、条件によって結論が変わる可能性がある点にはご注意ください。

## 避けること

- 根拠のない「明らかに」「必ず」「最強」などの強い断定
- 読者を煽るタイトルや、本文と釣り合わない大げさな表現
- 事実、引用、推測、個人的な好みを同じ確度で記述すること
- 用語を定義せず、略称だけで説明を進めること
- 箇条書きだけを並べ、項目間の関係を説明しないこと
- 過去記事の題材、経歴、結果、感情を新しい記事へ持ち込むこと
- 「参考になれば幸いです」「個人的には」などの特徴語を不自然に反復すること
- 長い導入、過剰なまとめ、同じ結論の言い換えによる水増し

## 最終セルフチェック

- 冒頭で目的と範囲が分かるか
- 概要を理解してから詳細へ進めるか
- 初出用語が必要十分に説明されているか
- 図表・数値・引用の意味を本文で解釈しているか
- 事実、観察、個人的解釈の境界が分かるか
- 断定の強さが根拠に合っているか
- 失敗や制約を都合よく省いていないか
- 各節が次の節へ自然につながっているか
- 結論が本文の証拠を越えていないか
- 文体上の特徴が口癖の連発になっていないか
